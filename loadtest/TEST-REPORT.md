# 撮合引擎压测报告

> 最新一轮：2026-11-13，HTTP c16 / HTTP c32 / kafkaTestBatch 三组 400k 对比，
> 以及撤单两批各 200k（c32）压测。
> 本轮环境：账户模块 ingress Disruptor 已删除（账户链路固定 poll 线程直连 listener），
> 下单入口 / 批量接口均使用当前工作区构建。
> 测试收尾时已清理压测工具、原始结果和应用日志；本文件为保留的唯一压测报告。

## 1. 测试环境与口径

| 项目 | 配置 |
|---|---|
| 机器 | 单机 4C/8T，7.9 GB 内存 |
| 组件 | Kafka 4.4.0 / MySQL / QuestDB 10.1.0 / 应用同机 |
| JVM | `-Xms512m -Xmx1280m -XX:+UseG1GC` |
| 用户 | 200 个用户预充值（USDT 1,000,000 / BTC 1,000 / ETH 10,000 每人） |
| 订单 | 每轮 400,000 单，BTC-USDT 200k + ETH-USDT 200k 交错提交 |
| 预热 | 每轮 10,000 单，预热排空后才开始计时 |
| 隔离 | 每轮重启应用并重新充值，避免内存态污染 |

**入口**

- HTTP：逐单 `POST /api/v1/currency/orders`，客户端并发 16 / 32；请求不携带 orderId，
  由币币模块生成。
- kafkaTestBatch：`POST /api/v1/currency/orders/kafka-test-batch`，每 2000 单一个请求，
  客户端 4 并发；请求不携带 orderId，服务端逐单生成后写入同一个下单 Disruptor。
  > 并发 16（16 × 2000 = 32,000 未消费事件）会把 65,536 的下单 ring 打满并出现 503，
  > 稳定口径使用 4。

**TPS 口径**

```
受理 TPS   = accepted / 灌入耗时
端到端 TPS = accepted /（全链路排空时刻 − 首批提交时刻）
```

- HTTP accepted = `202` 笔数；kafkaTestBatch accepted = 批量接口回执的 `accepted` 之和。
- 全链路排空 = order-command / account-order-freeze / order-freeze-result /
  account-trade-settlement 四个消费组 lag 回到基线（事务 commit marker 使 lag 常驻 1~2 条，
  判定为「lag ≤ 基线+2 且 topic LEO、lag 连续快照不变」）。
- marketdata / funds-batch 单独等待排空（off-path）。

| 2 | HTTP | 32 | 400,000 | 0/0/0 | 60.749 | **6,584.4** | 0.654 | 61.728 | **6,480.0** | 3.57 | 28.17 | 0 | 0 |
| 3 | kafkaTestBatch | 4 | 400,000 | 0/0/0 | 3.988 | **100,300.0** | 5.623 | 9.611 | **41,617.2** | 48.79* | 327.89* | 0 | 0 |

- 每轮 400,000 单全部受理，0 失败；应用日志无 `ERROR`、无异步拒单；

## 3. 对比结论

### 3.1 HTTP c16 → c32

| 指标 | c16 | c32 | 变化 |
|---|---:|---:|---:|
| 受理 TPS | 5,914.8 | **6,584.4** | **+11.3%** |
| 端到端 TPS | 5,815.0 | **6,480.0** | **+11.4%** |
| 灌入耗时 | 67.627 s | 60.749 s | −10.2% |
| p50 | 1.87 ms | 3.57 ms | +1.70 ms |
| p99 | 16.89 ms | 28.17 ms | +66.8% |

- 并发从 16 提到 32，吞吐只提升约 11%，单请求延迟接近翻倍（p50 1.87 → 3.57 ms）；
- 入口（Tomcat / JSON / 同步校验）仍是主要成本，继续加并发收益递减。

### 3.2 kafkaTestBatch vs HTTP c32

| 指标 | HTTP c32 | kafkaTestBatch | 对比 |
|---|---:|---:|---:|
| 灌入耗时 | 60.749 s | **3.988 s** | −93.4% |
| 受理侧 TPS | 6,584.4 | **100,300.0** | 约 15.2× |
| 清算链排空 | 0.654 s | 5.623 s | 8.6× |
| 总时间 | 61.728 s | **9.611 s** | −84.4% |
| 端到端 TPS | 6,480.0 | **41,617.2** | **6.4×** |

- 批量接口把 400k 单压缩为 200 个 HTTP 请求（每请求 2000 单），服务端逐单生成 orderId
  后写入同一 Disruptor；3.988 s 受理完，全链路再用 5.623 s 消化突发；
- 与历史结论一致：**HTTP/JSON 单笔入口是吞吐瓶颈**；批量接口受理侧提升约 15×，
  端到端提升约 6.4×；
- 批量轮排空时间更长，是因为 400k 单在 4 s 内集中涌入，队列等待集中在下游；
  HTTP 轮是 60~68 s 匀速灌入，下游边灌边消费。

### 3.3 数据完整性

三轮均满足：

- 单笔 / 批量接口全部返回 `202`，0 失败；
- `openOrders=0`（买卖全部撮合完成）；
- 汇总余额变化 `BTC=0, ETH=0, USDT=0`；
- 应用日志无异步拒单（余额不足 / 重复委托等）。

## 7. 撤单压测（两批各 200k，c32）

> 2026-11-13：HTTP 下 400k 不成交挂单（买 200k + 卖 200k），收集服务端生成的 orderId，
> 冻结链路排空后分两批各 200k 撤单，并发固定 32；撤单前用 10k 单预热。

### 7.1 方法

- 下单：HTTP 单笔接口，并发 32，共 400,000 单（买 200,000 + 卖 200,000）；
  BTC-USDT 买 50,000.00 / 卖 60,000.00（0.01 BTC），ETH-USDT 买 3,000.00 / 卖 4,000.00
  （0.1 ETH），买卖价格不交叉，全部挂单不成交；
- 从 202 响应收集服务端生成的 orderId，按提交顺序分成两批，每批 200,000；
- 撤单：`POST /api/v1/currency/orders/cancel`，并发 32；两批之间等待
  order-cancel + account-settlement 排空；
- 受理 TPS = 202 笔数 / 灌入耗时；端到端 TPS = 202 笔数 /（order-cancel +
  account-settlement 回到基线 − 首批提交时刻）。

### 7.2 结果

| 阶段 | 订单数 | 受理 | 失败 | 灌入耗时 s | 受理 TPS | 排空 s | 总时间 s | 端到端 TPS | p50 ms | p99 ms |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 下单（HTTP c32） | 400,000 | 400,000 | 0 | 52.077 | 7,680.9 | 0.995 | 53.248 | 7,512.0 | 3.21 | 22.33 |
| 撤单批次 1 | 200,000 | 200,000 | 0 | 27.484 | 7,276.9 | 1.670 | 29.203 | 6,848.7 | 3.45 | 21.03 |
| 撤单批次 2 | 200,000 | 200,000 | 0 | 26.344 | 7,592.0 | 1.966 | 28.345 | 7,055.9 | 3.41 | 20.14 |

### 7.3 完整性

- 下单 400,000 + 撤单 400,000 全部受理，0 失败、0 异步拒单；
- 结束后 `openOrders=0`，BTC / ETH / USDT 总余额变化均为 0；
- 两批撤单的 orderId 均来自下单 202 响应，未使用客户端指定 orderId。
