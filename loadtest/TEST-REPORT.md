# 撮合引擎压测报告

> 压测对象：当前工作区构建的单体撮合引擎（下单 → 冻结 → 撮合 → 清算 → 行情 / 委托历史归档）。
> 本报告以 HTTP c16 / c32 端到端压测为主口径；批量入口与撤单链路的历史测量仅作为方向性参考。

## 1. 测试环境与口径

| 项目 | 配置 |
|---|---|
| 机器 | 单机 4核8G |
| 组件 | Kafka 4.4.0 / MySQL / QuestDB 10.1.0 / 应用同机 |
| JVM | `-Xms512m -Xmx1280m -XX:+UseG1GC` |
| 用户 | 200 个用户预充值（USDT 1,000,000 / BTC 1,000 / ETH 10,000 每人） |
| 订单 | 每轮 400,000 单，BTC-USDT 200k + ETH-USDT 200k 交错提交 |
| 预热 | 每轮 10,000 单，预热排空后才开始计时 |
| 隔离 | 每轮重启应用并重新充值，避免内存态污染 |

**入口**

- HTTP：逐单 `POST /api/v1/currency/orders`，客户端并发 16 / 32；请求不携带 orderId，
  由币币模块生成。
- 批量接口（历史参考口径）：`POST /api/v1/currency/orders/kafka-test-batch`，每 2000 单
  一个请求，服务端逐单生成 orderId 后写入同一个下单 Disruptor。

**压测客户端**

- 当前 HTTP 压测使用**最小 HTTP/1.1 keep-alive 客户端**：每个并发一条长连接，手工拼接
  请求并按 `Content-Length` / chunked 编码读取响应，避免通用 HTTP 客户端在高并发下的
  额外开销。
- 历史口径使用通用 HTTP 客户端，其并发 16 已接近自身上限，因此跨口径的绝对数字
  **不能全部归因于服务端变化**；服务端热路径代码基本未变。

**TPS 口径**

```
受理 TPS   = accepted / 灌入耗时
端到端 TPS = accepted /（全链路排空时刻 − 首批提交时刻）
```

- HTTP accepted = `202` 笔数。
- 全链路排空 = order-command / account-order-freeze / order-freeze-result /
  account-trade-settlement 四个消费组 lag 回到阈值内。
- marketdata / funds-flow / order-history 三个 off-path 组单独等待排空。

## 2. 测试结果

| 轮次 | 并发 | 受理 | 失败(4xx/5xx/IO) | 灌入耗时 s | 受理 TPS | 清算排空 s | 总时间 s | 端到端 TPS | p50 ms | p99 ms | 残余挂单 | 余额差 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 16 | 400,000 | 0/0/0 | 43.180 | 9,263.6 | 0.230 | 43.410 | **9,214.5** | 0.89 | 8.81 | 0 | 0 |
| 2 | 32 | 400,000 | 0/0/0 | 46.274 | 8,644.2 | 0.480 | 46.754 | **8,555.4** | 1.99 | 28.04 | 0 | 0 |

- off-path 排空：c16 3.941 s、c32 1.338 s（含 order-history → QuestDB 归档）；
- 两轮 `ord_history` 均归档 410,000 行（400k 主轮 + 10k 预热），BTC / ETH 各 205,000 行，
  `status` 全部为 `FILLED`；
- 两轮结束后 `openOrders=0`，BTC / ETH / USDT 汇总余额变化均为 0；
- c32 应用日志 0 ERROR；c16 有 4 条 ERROR，均为前端页面轮询
  `/api/v1/orders/history` 与 `/api/v1/currency/funds-flows` 时 QuestDB JDBC 连接池
  获取超时（userId=1003），不经过下单 / 撮合 / 清算链路；两轮均无订单异步拒单。

## 3. 对比与结论

### 3.1 c16 → c32

| 指标 | c16 | c32 | 变化 |
|---|---:|---:|---:|
| 受理 TPS | 9,263.6 | 8,644.2 | **−6.7%** |
| 端到端 TPS | 9,214.5 | 8,555.4 | **−7.2%** |
| 灌入耗时 | 43.180 s | 46.274 s | +7.2% |
| p50 | 0.89 ms | 1.99 ms | +123.6% |
| p99 | 8.81 ms | 28.04 ms | +218.3% |

### 3.2 与历史参考口径对比

| 指标 | c16 历史参考 | c16 当前 | 变化 | c32 历史参考 | c32 当前 | 变化 |
|---|---:|---:|---:|---:|---:|---:|
| 受理 TPS | 5,914.8 | **9,263.6** | **+56.6%** | 6,584.4 | **8,644.2** | **+31.3%** |
| 端到端 TPS | 5,815.0 | **9,214.5** | **+58.5%** | 6,480.0 | **8,555.4** | **+32.0%** |
| 灌入耗时 | 67.627 s | 43.180 s | −36.1% | 60.749 s | 46.274 s | −23.8% |
| 清算排空 | 0.965 s | 0.230 s | −76.2% | 0.654 s | 0.480 s | −26.6% |
| 总时间 | 68.788 s | 43.410 s | −36.9% | 61.728 s | 46.754 s | −24.3% |
| p50 | 1.87 ms | 0.89 ms | −52.4% | 3.57 ms | 1.99 ms | −44.3% |
| p99 | 16.89 ms | 8.81 ms | −47.8% | 28.17 ms | 28.04 ms | −0.5% |

不同入口的历史参考（工具与版本不同，仅方向性对比）：

| 入口 | 受理 TPS | 端到端 TPS |
|---|---:|---:|
| HTTP c16（当前） | 9,263.6 | 9,214.5 |
| HTTP c32（当前） | 8,644.2 | 8,555.4 |
| 批量接口（历史参考） | 100,300.0 | 41,617.2 |

### 3.3 结论

- **c16 是当前 HTTP 入口的更优点**：并发从 16 提到 32，受理 / 端到端吞吐下降约 7%，
  p50 翻倍、p99 从 8.8 ms 升到 28 ms；继续加并发只增加排队与尾部延迟。
- 当前绝对吞吐明显高于历史参考口径，但**主要差异来自压测客户端**：历史通用客户端在
  c16 已接近自身上限，所以其 c16 → c32 还能提升约 11%；当前最小 keep-alive 客户端
  在 c16 已把服务端推到拐点。服务端热路径未做针对性优化，不能把提升全部归因于服务端。
- **HTTP 单笔入口仍是吞吐瓶颈**：批量入口历史参考为受理 100,300 TPS、端到端
  41,617 TPS，远高于 HTTP 的 9k 级；HTTP 侧应优先优化入口 / JSON / 校验，而不是继续
  加并发。
- 委托历史链路在 off-path 完成归档，410k 行全部落库，未拖慢主链路。
- c32 的 p99 与历史参考几乎一致（28.17 vs 28.04 ms），说明高并发尾部延迟受服务端排队
  主导；客户端优化主要改善中位延迟（p50 1.87 → 0.89 ms）。

## 4. 限制

- 压测客户端与服务端、Kafka、QuestDB 同机竞争 4核8G，数据不能直接外推到多机生产环境；
- Kafka 单节点 RF=1，`acks=all` 语义与多副本不同；
- 当前与历史参考的压测客户端不同，绝对数字用于同口径趋势对比；
- 订单构造为同价同量全成交，匹配成本接近最小值，复杂订单簿形态下吞吐可能不同。
